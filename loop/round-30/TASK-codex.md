## 一、`§5.2` 的五圈要是**連續**的一段，不是 3+2 兩段

### 現況

```js
const HEAP_RACE_LAPS = [3, 2];
```

而 `measureHeapRace()` 開頭就 `Page.navigate`。所以 `laps_measured = 5` 是
兩個獨立 session 的加總，**中間頁面重載，堆積被重置**。連續累積最長只有 3 圈。

### 為什麼這抵消了 R28 的用意

`BAR-PERF §5.2` 的說明欄寫的是——這是**唯一必須跑五圈才測得出來的指標**。
那句話只有在累積連續時才成立。兩個短窗口各自算「每圈成長」再平均，量到的
正是 `§5.2` 說不夠的那種單圈量測，只是平均了兩次。**任何只在第 4、5 圈才
顯現的洩漏（快取增長、事件監聽器堆積、物件池溢出）都看不到。**

R28 的結論本身不受影響：實測兩段的 `heapDelta` 都恰好是 0。但這個做法在真的
有洩漏時會系統性低估。

### 要求

- `HEAP_RACE_LAPS` 改成**單段五圈**，中間不重載
- 圈數判定維持 R28 的做法（`SimSnapshot` 的 lap 狀態，不是時間估算）
- 跑不滿五圈維持 `incomplete_five_lap_run` 明確 FAIL，不外推
- **如果有我不知道的原因非拆不可**（例如單段 150s 的 timeout 在你那邊會撞到
  什麼），不要硬改——回報原因，我來重新想 `§5.2` 的條文

### 順帶一提：`heapDelta` 恰好是 0 這件事本身值得查

兩段都是**精確的 0**，不是很小的數。可能是真的沒有洩漏（幀迴圈確實做成
零配置了），也可能是 `performance.memory.usedJSHeapSize` 的粒度太粗
（Chrome 未開 `--enable-precise-memory-info` 時會分桶到約 100KB）。

**請在 artifact 記下取樣的原始 byte 值**（不只是差值），讓「0 是真的沒長」
和「0 是解析度不夠」分得出來。這跟 `§2.5`／`§5.5` 在 R22 修的是同一件事。

## 二、`§4.1` 在算繪率低時測到的不是動畫，是取樣器的極限

### 現況

R28 這一輪 `§4.1` 量到 **10.087 FAIL**（窗口 `[11.5, 12.5]`，R26 是 11.846
PASS）。**但動畫一行都沒改**——`driver-face` 的量化實作從 R20 起沒動過。

原因是取樣定理：

```
renderedFrames 66、characterAnimationFrames 51 → 每幀 0.773
fps_p50 14.90、fps_p05 7.25
要解析 12Hz 的訊號，取樣率必須 > 24Hz
```

算繪率 14.9fps 時，每幀最多產生一次格變化，12Hz 的格必然被漏掉。
這是**量測極限，不是動畫缺陷**——跟 `§4.2`／`§4.3` 曾經「FAIL 的理由指錯
方向」是同一個家族，只是這次發生在低端。

### 不要用「算繪率不足就回報未判決」

那是最直覺的修法，也是錯的——它會做出另一個**永遠不會失敗的檢查**：
機器一慢，`§4.1` 就自動退場。這個專案已經在同一個坑裡跌過三次
（`§5.2` 的五秒、`§3.x` 的無節流、`§4.2/4.3` 的分母），不要再挖第四個。

### 正確的修法：把 `§4.1` 拆成強弱兩個判準

關鍵觀察是——**`characterAnimationPerFrame` 這個比值本身就能分辨動畫有沒有
被量化，而且不受算繪率影響**：

| 情況 | 比值 |
|---|---|
| 動畫改成逐幀平滑內插（`§4.1` 要擋的失敗模式） | **1.000** |
| 12Hz 量化，算繪率 F | **min(1, 12/F)** |

R28 實測 0.7727，而 `min(1, 12/14.9) = 0.805`。跟 1.000 差得很遠——
**即使在 14.9fps，「有沒有被量化」仍然分得出來**。分不出來的只有
「量化的頻率是不是恰好 12Hz」。

所以：

- **`fps_p05 > 24` 時**：維持現在的 Hz 窗口 `[11.5, 12.5]`。取樣率足夠，
  可以主張「量到 12Hz」
- **`fps_p05 ≤ 24` 時**：改判比值——`characterAnimationPerFrame` 必須
  **明顯低於 1.0**（建議上限 0.95，實測 0.77 有充足餘裕）。這仍然是一個
  **會失敗的檢查**：動畫一旦改成平滑內插，比值跳到 1.000 立刻 FAIL
- artifact 與 verdict 要**明確標示走的是哪一條**，弱判準的結論只能寫
  「證明有量化」，**不得寫成「證明是 12Hz」**

用 `fps_p05` 不是 `fps_p50`：慢幀才是漏格的來源，用中位數會讓一半的幀
不滿足取樣條件卻算過關。

### 要求

- `perf.py` 實作上面的兩條路徑，verdict 記下走哪一條
- 測試要涵蓋：高算繪率走 Hz 判準、低算繪率走比值判準、**比值 = 1.0
  在兩種算繪率下都 FAIL**（最後這條是證偽測試，一定要有）
- `BAR-PERF §4.1` 的條文我來改，你先把量測改好並回報實測數字
