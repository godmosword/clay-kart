## 使用者指認了「不夠流暢」的來源是轉向響應

R34 真人試玩回報「手感不夠流暢」，追問後指認為 **A：轉向響應**。

`§5` 目前有三項相關，**全部 PASS**：

```
5.1  steer_response_lag_ms   8.333   窗口 [0, 50]     ← 120Hz 的一個 tick，等於瞬間
5.3  yaw_settle_time_s       0.175   窗口 [0.15, .35]
5.4  yaw_overshoot_ratio     0       窗口 [0, 0.12]   ← 精確的 0
```

它量了「何時開始轉」「放開後多久停」「會不會轉過頭」，
**沒有任何一項量 yaw 速率怎麼爬上去**。

## 讀 code 找到兩個具體的東西

### 一、漂移時繞過了輸入平滑（`world.ts:506`）

```ts
const steeringInput = driftSteering ? this.#steer : this.#steerCommand;
```

平常走一階濾波過的 `#steerCommand`（`STEER_RISE_TIME_CONSTANT`），
**一進漂移就切成生的 `#steer`**。所以進出漂移的瞬間，yaw 速率是階躍的。

`§5.1` 的 8.333ms 是在非漂移路徑量的，量不到這個切換。

### 二、`yaw_overshoot_ratio = 0` 是結構性的，不是調得好（`world.ts:515`）

```ts
this.#yawRate = Math.abs(steeringRate) < 1e-9 ? 0 : steeringRate;
```

`#yawRate` 是**直接指派**，不是積分——它是「當下的轉向指令 × 速度因子」的
純函數，**沒有任何角動量**。所以它在結構上不可能過頭，`§5.4` 恆為 0。

**這是這個專案追了九次的那個家族的第十例**：數字有在跑，但它不可能失敗。
而且這次它同時就是手感問題本身——沒有角動量的車，轉向沒有重量。

## 這一輪只做量測，不要調參數

**明文禁止在這一輪改任何物理常數或響應曲線。** 理由：

- `BAR-FEEL` 46 項裡 `§4.10` 的餘裕是 0.00028、`§4.6` 是 1.88%、`§12.3` 是 0.098%。
  轉向與速度耦合（`speedFactor`），動它很可能推掉那幾項
- 更重要的：**現在沒有任何指標能判斷「調完有沒有比較好」**。
  先有尺，再調。這正是 R17–R29 視覺線的教訓——量測壞掉的時候調了十三輪

### 要求：補三項量測

1. **`yaw` 速率的上升曲線**：從 steer 階躍輸入到 yaw 速率達到目標值 90% 的時間，
   以及上升過程中 yaw **角加速度**的最大值與 sd。
   （`§5.1` 只量「開始動」，這個量「怎麼爬」）
2. **進出漂移的 yaw 速率不連續量**：漂移狀態切換的那一個 tick，
   yaw 速率的變化量絕對值。**這直接量第一個發現**。
3. **`§5.4` 的誠實化**：在 artifact 裡標明 `yaw_overshoot_ratio` 目前
   **在結構上不可能非零**（`#yawRate` 是直接指派、無角動量）。
   窗口先不動，但那個 `0` 不該再被讀成「調得好」。

三項都先只進 artifact 的 `meta` 或新欄位，**不要加進 `WINDOWS`**——
還沒有人知道合理的窗口是多少，現在定窗口就是憑空編。
